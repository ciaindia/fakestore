Stockroom Ledger (React Edition)

A Comprehensive React Basics CRUD Application with Components, Controlled Forms, Hooks & REST Integration

VERSION: 2.0 (React) TARGET: REACT 18 / 19 STATUS: APPROVED FOR BUILD FOCUS: HOOKS & PROPS

1. Overview & Purpose

Vision

Stockroom Ledger (React Edition) is an interactive single-page inventory catalog designed to teach and demonstrate foundational React engineering principles through an end-to-end CRUD (Create, Read, Update, Delete) product management workflow. Using the public Fake Store API as its mock REST backend, the application illustrates how real-world React frontends handle component decomposition, props communication, state orchestration, lifecycle effects, and controlled user inputs.

Rather than relying on heavyweight abstractions like Redux, Zustand, or full-stack frameworks (Next.js/Remix), this project stays intentionally centered on standard React primitives: functional components, JSX templating, useState, useEffect, useMemo, and custom hooks.

2. Problem & Learning Gap

Context

Beginner and intermediate developers transitioning from vanilla JavaScript to React frequently encounter a steep conceptual hurdle: tutorials typically build trivial "counter" buttons or standalone "to-do lists" with hardcoded data. When tasked with building an actual application that interacts with a network API, manages tabular/card grids, updates data in place, and validates forms, they face major pitfalls:

  • State mutation bugs: Directly modifying arrays or objects instead of creating immutable copies with setState.
  • Overusing or misusing useEffect: Triggering infinite fetch loops, missing dependency array entries, or not cleaning up async operations.
  • Props drilling confusion: Inability to cleanly lift state up or pass callback event handlers (e.g. onDelete, onEdit) to child cards.
  • Uncontrolled vs. Controlled inputs: Struggling to sync form fields with React component state and validate inputs before API dispatch.

This PRD establishes a definitive blueprint for an educational yet production-grade reference project that bridges these gaps.

3. Goals & Core Concepts

Scope

The primary outcome of this project is mastery of fundamental React mental models and patterns:

  • Component Modularity: Decomposing a rich UI into single-responsibility, reusable presentational and container components.
  • Unidirectional Data Flow: Passing data down via props and bubbling events up via callback functions.
  • Local State Management: Managing UI state (search queries, active filters, modal states) and entity state (products list) with useState.
  • Lifecycle & Side Effects: Handling API data fetching and error states cleanly with useEffect and AbortController.
  • Controlled Forms: Building reliable two-way bound inputs with validation states for both Create and Edit modes.
  • Derived State & Memoization: Filtering and searching data on the fly using useMemo without duplicating state in memory.

Explicit Non-Goals

  • External state management libraries (no Redux, Zustand, Recoil).
  • Client-side routing (single-page dashboard layout keeps focus on state fundamentals).
  • Complex database persistence (the project gracefully simulates writes against Fake Store API).
  • Heavy CSS UI component libraries (styled with clean CSS modules or vanilla CSS to highlight DOM structure).

5. Functional Requirements

CRUD Specs

5.1 Read: Product Catalog & Feed

  • On initial component mount (useEffect), fetch the initial 20 items from GET https://fakestoreapi.com/products?limit=20.
  • Display items in a responsive grid of <ProductCard /> components.
  • Render explicit visual states:
    • Loading State: Display animated skeleton cards while the request is in-flight.
    • Error State: Display a retry banner if the network request fails.
    • Empty State: Display "No products match your criteria" if a search/category filter produces 0 results.
  • Live statistics banner showing total items loaded and visible results count.

5.2 Create: Add Product Modal/Drawer

  • An "+ Add Product" button opens a controlled <ProductFormModal />.
  • Controlled form fields:
    • title (text, required, min 3 chars).
    • price (number, required, must be > 0).
    • category (select: electronics, jewelery, men's clothing, women's clothing).
    • image (URL text input with real-time preview, optional fallback).
    • description (textarea, optional).
  • Validates fields on blur and submit; displays inline error text.
  • On submit, dispatches POST /products, prepends the new item to the React state array optimistically, and displays a temporary success toast notification.

5.3 Update: Edit Product Mode

  • Each <ProductCard /> includes an "Edit" button that passes the product object up to parent state.
  • The <ProductFormModal /> opens populated with the existing product's attributes.
  • The modal switches to "Edit Mode": shows an ID badge, changes submit button to "Save Changes", and enables a "Cancel" button.
  • On submit, dispatches PUT /products/:id, updates that specific item in the React state array immutably via products.map(...), and closes the modal.

5.4 Delete: Remove Product with Confirmation

  • Each card features a "Delete" button that triggers a confirmation modal: "Are you sure you want to delete this product?"
  • On user confirmation, dispatches DELETE /products/:id.
  • On response, immutably removes the item from state: setProducts(prev => prev.filter(p => p.id !== targetId)).
  • Triggers a success toast notification confirming deletion.

5.5 Real-Time Search & Category Filtering

  • <SearchBar />: Controlled input for instant title filtering (case-insensitive substring match).
  • <CategoryFilter />: Horizontal pills/chips ("All", "Electronics", "Jewelery", etc.) to toggle category selection.
  • Filter logic is implemented as a derived state using useMemo, ensuring the raw products array remains intact in parent state.

6. Component Architecture & Hierarchy

Structure

The application follows a clean unidirectional component hierarchy. State is maintained at the lowest common ancestor (<App /> or dedicated container), and child components receive data and event handlers strictly through props:

React Component Tree & Prop Flow
<App /> // Root Container: holds products, filter, search, activeModal state
  ├── <Header /> { onOpenCreateModal }
  ├── <Toolbar />
  │     ├── <SearchBar /> { query, onQueryChange }
  │     └── <CategoryChips /> { categories, activeCategory, onSelectCategory }
  ├── <StatsBar /> { totalCount, filteredCount, isLoading }
  ├── <ProductGrid />
  │     ├── <LoadingSkeleton /> // Rendered when isLoading === true
  │     ├── <EmptyState /> // Rendered when filteredProducts.length === 0
  │     └── <ProductCard /> { product, onEdit, onDeleteRequest } (mapped x N)
  │           ├── <RatingBadge /> { rating }
  │           └── <CardActions /> { onEdit, onDelete }
  ├── <ProductModal /> { isOpen, mode, initialData, onSubmit, onClose }
  ├── <DeleteConfirmModal /> { isOpen, product, onConfirm, onCancel }
  └── <ToastContainer /> { toasts }

Component Responsibility Breakdown

Component Type Key Responsibilities
<App /> Container / Smart Fetches data, manages product list, filter query, selected product for edit, and toast queues.
<ProductGrid /> Layout Renders the responsive CSS grid; handles empty and loading skeleton states.
<ProductCard /> Presentational Receives a single product object; emits onEdit(product) and onDelete(product.id).
<ProductModal /> Controlled Form Maintains internal form state, executes field validations, and emits formatted payload on submit.

8. State & React Hooks Design

Mechanics

Proper state scoping is central to writing clean React code. The table below outlines how state is distributed and which built-in React hooks govern each behavior:

State Identifier Hook Used Component Owner Purpose & Immutability Rule
products useState([]) <App /> Array of all active product items. Updated via immutable transforms ([...prev, item], .map(), .filter()).
searchQuery useState("") <App /> String tracking search input. Controls derived filtering in real-time.
selectedCategory useState("all") <App /> String representing active category chip.
modalConfig useState(null) <App /> Object: { isOpen: boolean, mode: 'create'|'edit', product?: Product }.
formData useState(initial) <ProductModal /> Local controlled form state. Handles field changes and reset on close.
filteredProducts useMemo(...) <App /> Derived state: computed from products, searchQuery, and selectedCategory without extra state.
React Fundamentals Tip: State Immutability
Never mutate state directly! When modifying the products array:
  • Create: setProducts(prev => [newProduct, ...prev]);
  • Update: setProducts(prev => prev.map(p => p.id === updated.id ? updated : p));
  • Delete: setProducts(prev => prev.filter(p => p.id !== id));

9. Non-Functional Reqs & Best Practices

Quality
  • Strict Mode Compliance: Must run cleanly under React 18/19 <React.StrictMode> without duplicate effect side-effect bugs or memory leaks.
  • Unique and Stable Keys: Every mapped element in <ProductGrid /> must use a unique identifier (e.g., key={product.id}). Never use array indexes as keys for dynamic lists.
  • No Direct DOM Access: Zero occurrences of document.getElementById() or direct DOM manipulation. All DOM modifications occur through React state and refs (if necessary).
  • Clean Folder Organization:
    src/
    ├── components/         // Reusable presentational components
    │   ├── Header.jsx
    │   ├── ProductCard.jsx
    │   ├── ProductGrid.jsx
    │   ├── ProductModal.jsx
    │   ├── SearchBar.jsx
    │   └── Toast.jsx
    ├── services/           // API fetch helper modules
    │   └── api.js
    ├── App.jsx             // Main container with state & effects
    ├── main.jsx            // React entrypoint
    └── index.css           // Global styles & variables
  • Accessibility Baseline: Modals trap focus and can be dismissed via the Escape key. Form inputs carry appropriate <label htmlFor="..."> tags.

10. React Gotchas & Limitations

Constraints
Mock API Behavioral Constraints
  • Non-Persistent Backend: The Fake Store API responds with successful HTTP 200/201 status codes and JSON representations for POST, PUT, and DELETE, but it does not persist changes in a real database. Local React state must act as the ultimate source of truth during the user session.
  • Client-Generated IDs: Creating a new product returns a placeholder ID from Fake Store API (often 21). The client should handle potential duplicate ID conflicts by appending timestamps or using crypto.randomUUID() for new local items.
  • Asynchronous State Batching: State updates in React 18+ are batched. Learners must use updater functions (e.g. setCount(c => c + 1)) whenever the new state depends on the previous state.

12. Roadmap & Next Steps

Extensions

Once the core React basics are implemented, students can level up their architecture with these sequential milestones:

  1. Context API Integration: Introduce a ThemeContext (Light/Dark mode) and a CartContext to experience global state without props drilling.
  2. Custom Hook Extraction: Refactor data fetching and mutations into a reusable useProducts() custom hook.
  3. Debounced Search: Implement a useDebounce() hook on the search input to simulate realistic search querying.
  4. React Router v6: Expand the single-page catalog to include dynamic routes (/products/:id) for dedicated product detail views.
  5. Local Storage Synchronization: Persist user-created and updated products to browser localStorage so changes survive page reloads.
