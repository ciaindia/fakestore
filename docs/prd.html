1. Overview

Stockroom Ledger is a single-page web application that lets a user create, view, update, and delete product entries against the Fake Store API. It exists as a lightweight reference implementation for demonstrating full CRUD interactions using the browser's native Fetch API, with no build tooling, frameworks, or backend of its own.

2. Problem Statement

Developers evaluating the Fake Store API, teaching Fetch API fundamentals, or prototyping a product-management UI need a minimal, self-contained example that exercises all four CRUD operations against a real (if mock) REST endpoint. Existing examples are typically split across multiple files, require a build step, or only cover reads. There's no single-file, copy-pasteable reference that shows create, read, update, and delete together with realistic error handling.

3. Goals

  • Provide a working, single-file HTML example of CRUD via fetch().
  • Make the mock API's non-persistence behavior transparent rather than confusing.
  • Keep the UI usable enough to serve as a real demo, not just a code sample.

Non-goals

  • Real data persistence (Fake Store API does not save writes; this is a known and accepted limitation).
  • User authentication or authorization.
  • Multi-user or real-time collaboration.
  • Production-grade inventory management (stock counts, SKUs, variants, etc.).

5. Functional Requirements

5.1 Read (List Products)

  • On load, fetch up to 20 products from GET /products?limit=20.
  • Display each product as a card: image, title, price, category tag, truncated description.
  • Show a loading state while the request is in flight.
  • Show a clear error state if the request fails.
  • Provide a manual "Reload from API" action.
  • Display a live count of items currently shown.

5.2 Create (Add Product)

  • Form fields: title (text, required), price (number, required, greater than 0), category (select), image URL (optional, falls back to a placeholder), description (textarea, optional).
  • Validate required fields client-side before submission; show inline error messages.
  • On submit, POST /products with the form payload as JSON.
  • On success, prepend the new item to the grid and clear the form.
  • On failure, show an error message and preserve form input.

5.3 Update (Edit Product)

  • "Edit" action on any card loads that product's data into the form and switches it into edit mode.
  • Edit mode is visually distinct (badge showing the record ID, submit button relabeled "Save changes", a "Cancel" action appears).
  • On submit, PUT /products/:id with the updated payload.
  • On success, update the corresponding card in place and exit edit mode.
  • "Cancel" discards changes and returns the form to create mode.

5.4 Delete (Remove Product)

  • "Delete" action on any card prompts for confirmation before proceeding.
  • On confirmation, DELETE /products/:id.
  • On success, remove the card from the grid immediately.
  • If the deleted item was being edited, the form resets to create mode.

5.5 Error Handling

  • All network calls are wrapped in try/catch.
  • Non-2xx responses surface a specific, human-readable message (e.g., "PUT failed: 500") rather than failing silently.
  • The app never leaves the UI in an ambiguous loading state on error.

6. Wireframe

The listing view follows a familiar e-commerce grid pattern (similar to Flipkart's product listing): a search bar and filter chips up top, then a responsive grid of product cards. Each card keeps the same anatomy — image, title, rating badge, price with a struck-through original price and discount percentage, and an "Add to cart" action — so the eye can scan the grid quickly without re-learning the layout per item.

Fig 1 — Product listing grid, Flipkart-style layout

Key layout decisions this implies for the current app:

  • Cards keep a fixed visual rhythm (image → title → rating → price → action) rather than varying by product.
  • Discount/rating badges are optional per item, but the card frame stays the same size whether or not they're present, so the grid doesn't look ragged.
  • Filter chips are implemented as a category filter in the current build (see Section 8).

7. Non-Functional Requirements

  • Zero dependencies: plain HTML/CSS/JS, no build step, works by opening the file directly in a browser.
  • Responsive: usable from ~360px mobile width up through desktop; form and grid stack on narrow viewports.
  • Accessibility baseline: labeled form fields, visible focus states, sufficient color contrast.
  • Performance: initial product list capped at 20 items to keep the demo snappy; images lazy-load.
  • Resilience to mock-API quirks: because Fake Store API doesn't persist POST/PUT/DELETE server-side, the app reconciles local state after each write so the UI reflects the user's intent even though a fresh page reload from the API would not show those changes.

8. Technical Design

  • Endpoint base: https://fakestoreapi.com/products
  • Methods used: GET, POST, PUT, DELETE, all via the native fetch() API with application/json bodies.
  • State model: a single in-memory products array is the source of truth for rendering; it is patched optimistically after each successful write and re-rendered.
  • Category filter chips and a title search box filter the in-memory array client-side; no additional endpoints are involved.
  • No routing, no persistence layer, no external libraries.

9. Known Limitations

  • Data does not persist across page reloads — this is a constraint of the underlying mock API, not the app.
  • New product IDs are client-generated approximations since the API doesn't return stable new IDs.
  • Discount price and percentage are derived locally for display purposes; the API doesn't provide a real "original price" field.
  • No pagination beyond the initial 20-item fetch.
  • No image upload; images are URL-only.

10. Success Criteria

  • A user can perform all four CRUD operations end-to-end without opening dev tools.
  • Every network failure produces a visible, specific message.
  • The file runs standalone with no console errors on load.

11. Future Considerations

  • Swap the mock API for a real backend with actual persistence.
  • Add sort-by-price and multi-select filtering alongside the existing category chips.
  • Add pagination or infinite scroll for larger catalogs.
  • Add optimistic UI rollback if a write fails after an in-place update.
